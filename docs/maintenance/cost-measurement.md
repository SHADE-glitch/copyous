# 成本口径：空闲 CPU、RSS 与滚动代价怎么读

凡是「快了多少 / 省了多少内存 / 空转费不费电」的结论都要落在这个文件的口径上，否则两个数不可比。

> **来历**：RSS 高水位与"滚动成本不设闸"两条是从 `MAINTENANCE.md`（拆分前 520 行 / 12 节）第 5 节逐字搬来的；
> 空闲 CPU 那一段是 2026-10-09 新写的，并且**当场跑过**（数据就在下面，包括跑坏的那一次）。
> 这个文件是这些事实的唯一主人，别在别处复述一遍。

## 1. 空闲 CPU：只能差分，而且差分的对象是同一个进程

**为什么不能直接看**：真实会话里整个 gnome-shell 30 秒采样能读到 ~48% 单核，这个数字**完全不可归因**
—— 里面有合成器、.index 重建、其它扩展、用户的鼠标动作。把它当"扩展的成本"是错的，历史上我错过一次。

**方法**：`test/headless/idle-cost.sh [窗口秒] [轮数]`（默认 30 3）。同一个 headless 进程里测两个静默窗口，
相减：

1. `up.sh` 起隔离 shell（私有 dbus、memory 后端、fixture 库副本 —— 与探针完全同一套隔离）。
2. 起壳后先静置 15 s，再跑一个**丢弃窗口**，然后才跑**测量窗口**。
3. `ExtensionSystem._callExtensionInit/Enable` + 等 255 条填充稳定，静置 20 s，同样丢弃一个窗口再测一个。
4. 读数取 `/proc/<pid>/stat` 的 `utime+stime+cutime+cstime`，窗口两端各读一次做差。

**为什么是 jiffies 而不是采样**：这四个字段是**计数器**，没有采样混叠、没有 profiler 开销、不受
swap 抖动影响。代价是分辨率 = 1 tick = 10 ms CPU。45 s 窗口下 1 tick = 0.022% 单核。

**为什么两个窗口前面都要放一个丢弃窗口**（这是这台仪器唯一的真陷阱）：第一次跑（30 s ×3、3 轮）报的是
**负 delta**：

```
round   off_cpu_s   on_cpu_s   delta_s
    1       0.370       0.280    -0.090
    2       0.390       0.180    -0.210
    3       0.390       0.170    -0.220
```

不是"扩展省 CPU"，而是**顺序偏差**：OFF 窗口落在 t≈15–45 s，那时 shell 还在做延迟工作（主题、
按需 D-Bus 激活），ON 窗口落在 t≈110 s 之后，shell 已经彻底安静。加了丢弃窗口之后同一个量变成：

```
round   off_cpu_s   on_cpu_s   delta_s   delta_pct   enable_one_shot_s
    1       0.100       0.120     0.020       0.050             0.500
    2       0.060       0.050    -0.010      -0.020             0.520
mean idle delta over 2 rounds : 0.005 CPU-seconds per 45s window
instrument resolution             : one tick = 10.0 ms of CPU = 0.022% of a 45s window
VERDICT: NOT MEASURABLE -- mean is under one tick per window. Do not record this as "zero cost".
```

**结论（写下来，别再重测）**：这个扩展**空转不耗电** —— 空闲增量小于仪器分辨率。
shell 本体在 headless 下静置后是 0.06–0.10 CPU-s / 45 s（约 0.13–0.22% 单核），扩展开完 255 条之后
读数没有可辨化。
**这条结论的边界要说清楚**：它说的是"什么都不做的时候"。**复制、搜索、打开对话框的成本在
探针 05/10 里量**（主线程被钉住的毫秒数），那才是会卡的量；CPU 差分看不见一个几十毫秒的同步卡顿（F3 实测 24–46ms 那一类），
它在 45 s 窗口里连一次 tick 都算不满。所以：**"能不能感到卡"用阻塞毫秒数，"要不要一直烧电"用这台差分仪。**

**能测到的那一个数**：`enable_one_shot` 五次 0.600 / 0.520 / 0.500（第一轮）+ 0.500 / 0.520（第二轮），
极差 0.10 s（init + enable + 255 条填充 + 建条目）。这是登录时的一次性支出，稳定可复现，
值得当回归线：**哪天它涨到 1.0 就是有人在 enable 路径上做了同步 IO 或全量遍历**。

## 2. 内存：RSS 是高水位，不是活集

- **不能**：RSS 的绝对值。glibc 不把释放掉的 GJS 内存还给 OS，RSS 是**高水位**，走完整个列表后
  不会回落。窗口化赢在"正常使用时到不了那个水位"，不赢在回收。

- **滚动成本只报数不设闸**：每跨一屏中位 ~18ms 是窗口化的**代价**（销毁+重建约 2 个 item），
  不是回归。写进阈值会把一个已知的好交易变成红灯。一屏 overscan 以内的小滚动仍是零成本。

判一次真实回归的代价：需要注销登录。别指望 disable/enable。

## 3. 泄漏怎么读（仪器已有，这里只定口径）

常驻集与"disable 之后还剩什么"由**探针 09** 测（`live 09`：`entryTextsRetainedAtDisable` +
disable 前后 RSS 两个数）。口径三条：

1. RSS **只报数不作判据** —— GJS 没有确定回收点，"没降"不等于"漏了"。真正的判据是
   *对象还在不在*（`_matchCache`、`_items`、`_entries` 这些活引用），不是内核记账。
2. 同一会话里**二次 enable 是 harness 禁区**（绕过管理器会让 `disableExtension()` 变空操作），
   所以"重复 enable/disable 是否泄漏"这条只能在真实会话里验，见 [verification.md](verification.md)。
3. 多轮趋势看**中位数**不看峰值：这台笔记本在重 swap 下，单次 RSS 尖峰可以完全由换页造成。

## 4. 什么数不能当判据

| 数 | 为什么不能 |
| --- | --- |
| 整 shell CPU% | 不可归因（第 1 节开头） |
| 未加丢弃窗口的 CPU 差分 | 顺序偏差，会把仪器读成"扩展省 CPU" |
| RSS 绝对值 | 高水位，不是活集 |
| 滚动中位耗时 | 是窗口化的已知代价，不是回归 |
| 任何比例型阈值 | 同一份代码三次跑出 1.3 / 1.57 / 1.72，阈值只能制造假红（见 [reading-the-log.md](reading-the-log.md)） |
| headless 的 `fillMs` | 实测 3.9–4.5 s（探针 04/05/06 的 `metrics.fillMs`，255 条 fixture），和真实会话不同尺 —— 那边登录填充是另一套数，只能**同臂自比**，别拿它和 [baseline.md](baseline.md) 的数对照 |
